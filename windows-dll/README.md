# Windows QEMU DLL — Phase 1 (DLL-link proof)

Decision: QEMU Option A first (Windows QEMU library build, DLL), Option B
(subprocess redesign) as fallback only if A blocks. This directory holds the
Phase 1 artifacts: everything needed to link `qemu-arm.dll` from the
`qemu-system-arm` build and smoke it, and nothing else. No Phase 2
(`Qemu.swift` LoadLibrary path) or Phase 3 (helper modes) work lives here.

## Files

- `qemu-arm.def` — the DLL export list: 55 `qemu_ios_*` names, no leading
  underscore, machine-extracted from the macOS script's own SYMS list
  (`contrib/macos-app/make-dylib-macos.sh` at the pinned commit). NOT 62:
  the 62-count in `DYLIB_RELINK_NOTES.md` includes 7 declarations that the
  macOS dylib does NOT export (`battery_config`, `ui_cancel_input`,
  `ui_manual_touch2`, `set_foreground`, `vm_started`, `vm_stopped`,
  `frame_size`); `macos-exports.syms` is generated by that script, not a
  repo file, which is why it 404s at the pin.
- `make-dll-windows.sh` — MinGW adaptation of `make-dylib-macos.sh`:
  compile `qemu-ios-entry.c` + `qemu-ios-ui.c` + (patched)
  `qemu-macos-extras.c` with the build's own flags, steal ninja's link
  line for `qemu-system-arm`, rewrite it (drop `-o`, swap
  `system_main.c.o` for the three entry objects, drop `@*.syms`,
  replace the `@response-file` token with the LINK edge's explicit link
  objects from `build.ninja` instead of expanding `@response-files` —
  ninja generates the rsp on demand and it is gone by step-14 time
  (branch b, run 40788851368), so replaying the rsp-based link line by
  hand cannot work, and the exe's objects live in the libraries' `.p`
  dirs via `extract_all_objects`, not in `qemu-system-arm.exe.p`
  (branch b-v2, run 40798501224). Pass 1 prints the edge's input suffix
  histogram first and accepts `.obj` (meson on Windows uses `.obj`, not
  `.o` — run 40807517166 proved the `.o`-only filter + `.o`-only swap
  silently dropped the bulk and the entry objects); the swap fails fast
  if no `system_main` object is found. Pass 2 then moves the objects
  (including the swapped entry objects) one-per-line into a NEW
  response file (`windows-link-objs.rsp`); the link runs as
  `<compiler> @windows-link-objs.rsp <flags/archives> -shared -o
  qemu-arm.dll qemu-arm.def`, because 1172 object paths (~70KB)
  exceed Windows' 32,768-char command-line limit and a direct
  invocation dies with 'Argument list too long' (run 40816130822) —
  the exe link itself uses `@qemu-system-arm.exe.rsp` for the same
  reason. The `@rsp` token takes the first object's position so the
  compiler stays first. No undefined-symbol tolerance
  exists for Windows DLLs; the link must resolve everything.
- `qemu-windows-extras.patch` — applied to `qemu-src` BEFORE configure
  (same pattern as the workflow's `win32-portability.patch`). Three
  `_WIN32` guards, macOS build byte-identical: (1) `dlfcn.h` +
  `mach-o/loader.h` includes (serve only `build_id`); (2) `key_mac` stub
  (silent no-op, matching this function's existing ignore-unmapped-keys
  behaviour — the osx keymap table does not exist on Windows); (3)
  `build_id` stub returning NULL (the function's existing "identity
  unavailable" signal; the helper's `buildID` is optional, so NULL is
  downstream-safe). Verified: `git apply --check` passes on pristine
  `qemu-macos-extras.c` at pin `cb3595e8…`.
- `qemu-dll-smoke.c` — the smoke proof. `LoadLibrary` +
  `GetProcAddress(device_info_at, build_id, api_version)` + call all three
  WITHOUT booting a VM (`device_info_at` is valid before `qemu_ios_main`,
  no lock). Exit 0 only if all three resolve and all three calls return.
  `build_id` NULL is a PASS (Windows stub, see above);
  `device_info_at(0)` NULL is a FAIL (no machines compiled in).

## Consumption (workflow step, port repo — not in this commit)

A `windows-emulator-ci` step after Build, before Bundle, on a port-repo
branch (parent's push/merge call): fetch this directory at a pinned commit
of lighttouch-emulator, `git apply qemu-windows-extras.patch` in `qemu-src`
(it must land before the entry objects compile — patch before Configure is
simplest, matching the existing patch steps), run
`make-dll-windows.sh qemu-src qemu-src/build qemu-arm.def`, compile
`qemu-dll-smoke.c` with MinGW gcc, run the smoke against
`qemu-src/build/qemu-arm.dll`, and upload the DLL (same artifact or a new
one). The smoke run IS the Phase 1 proof: runtime behaviour on Windows CI,
not compilation alone.

## What this does NOT prove

- That the DLL links: the entry/UI sources are NOT compiled by the exe
  build, so MinGW compile errors there surface only at this step.
- That `key_mac` / `build_id` work on Windows: both are honest stubs
  (documented above). Proper ports (win32 keymap -> qcode; PE-based
  identity) are future work, not Phase 1.
- That the helper runs on the DLL, or that any device boots: that is
  Phase 2 (loader path) and Phase 3 (modes), gated on Phase 1 proof +
  main-agent confirmation.

## Stop condition (hard, from the Phase 1 assignment)

If this step blocks on the MinGW/Swift boundary or on extras porting
(entry/UI compile failure, DLL link failure on undefined symbols, or a
smoke failure), STOP and report the block with evidence. Do not sink
unbounded time, do not start Phase 2 or 3, and do not paper over a link
failure with an export-all flag. Pivoting to Option B is the main agent's
next decision.
